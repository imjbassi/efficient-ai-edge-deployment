\section{Introduction}
\label{sec:intro}

Executing inference near the data source can reduce network dependence and response time, but edge devices impose tight limits on storage, memory, computation, and power. Integer post-training quantization (PTQ) is attractive because it can reduce model storage by approximately fourfold and enable integer kernels \cite{jacob2018quantization,tflite_integer}. This storage argument follows directly from representation width; the latency argument does not. Realized speed depends on graph structure, kernel coverage, delegate selection, threading, and hardware \cite{reddi2020mlperf,li2021mqbench,wang2023spaceevo}.

MobileNetV2 is a useful audit subject: it is a canonical compact architecture built from depthwise separable convolutions and inverted residual blocks \cite{sandler2018mobilenetv2}, and its PTQ workflow is mature enough that conversion alone is not a research contribution. The interesting question is therefore narrower and testable: under what runtime and quantization conditions does an otherwise fixed INT8 model remain accurate and become faster?

This work contributes an empirical audit and its public executable artifact, not a new quantization algorithm. It is intentionally host-side: x86 CPU and container measurements isolate software-stack effects before future replication on ARM hardware. It makes three claims. First, per-channel INT8 preserves useful accuracy while a per-tensor control does not. Second, INT8 speedup is conditional: it is modest with the default XNNPACK delegate and reverses on a built-in-kernel counterfactual. Third, packaging costs are measurable system properties rather than prose-level design details. The artifact supplies paired predictions, raw timings from independent processes, model and dataset hashes, container measurements, and one entry point that regenerates every reported quantity.

\section{Related Work and Research Questions}

Integer-only inference has a well-established algorithmic basis. Jacob et al. described affine quantization, integer arithmetic, and training procedures that made eight-bit deployment practical across mobile models \cite{jacob2018quantization}. Subsequent tooling made PTQ a routine conversion path, but the convenience of conversion can obscure two distinct validation problems: whether the quantized graph preserves predictions and whether the selected runtime has efficient kernels for that graph. MQBench formalized the need to separate simulated quantization quality from deployable backend behavior \cite{li2021mqbench}. SpaceEvo similarly showed that INT8 latency is architecture- and hardware-dependent, motivating search spaces designed around actual low-precision execution rather than floating-point proxies \cite{wang2023spaceevo}.

Benchmark suites address a complementary systems problem. MLPerf Inference, Mobile, and Tiny specify scenarios and measurement rules because latency numbers are otherwise inseparable from hardware, software, and load assumptions \cite{reddi2020mlperf,reddi2020mobile,banbury2021mlperf}. This study is smaller in model and platform scope, but applies the same principle to an inspectable end-to-end artifact. It also distinguishes native interpreter latency from HTTP and container measurements, which have different timed boundaries.

The audit is organized around three research questions. \emph{RQ1:} Does full-integer PTQ preserve accuracy under per-channel and per-tensor weight quantization? \emph{RQ2:} How does the FP32/INT8 latency ratio change with delegate, thread count, and batch size when uncertainty is estimated across fresh processes? \emph{RQ3:} What image-size, cold-start, memory, and request-latency costs accompany the deployable container? These questions turn a familiar conversion recipe into falsifiable claims about correctness and realized system behavior.
