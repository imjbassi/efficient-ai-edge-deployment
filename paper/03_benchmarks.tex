\subsection{Accuracy depends on granularity}

Table~\ref{tab:accuracy} shows that per-channel INT8 retained most FP32 accuracy while reducing storage from 13.34 to 3.81 MiB (71.5\%). The top-1 comparison is not merely two overlapping marginal intervals: among the same 3,925 images, 125 were correct only for FP32 and 89 only for INT8. The resulting $-0.92$ percentage-point difference has paired bootstrap 95\% CI $[-1.66,-0.18]$ and exact McNemar $p=.0165$. Top-5 changed by $-0.94$ points (76 FP32-only versus 39 INT8-only; CI $[-1.48,-0.41]$; $p=.00072$).

The per-tensor control was 10.2\% smaller than per-channel INT8 but achieved only 1.04\% top-1 and 3.95\% top-5 accuracy. Since its one-thread XNNPACK latency (7.96 ms; 95\% CI $[7.53,8.39]$) was close to per-channel INT8, the failure is numerical rather than a latency tradeoff. Quantization granularity is therefore part of model correctness, not a packaging detail.

\subsection{Speedup depends on the execution backend}

The one-thread XNNPACK condition is the primary latency comparison. FP32 and per-channel INT8 mean-of-run-means were 10.72 ms (95\% CI $[9.79,11.65]$) and 7.55 ms ($[6.18,8.91]$), respectively. Matched run ratios yield a 1.43$\times$ geometric-mean speedup ($[1.18,1.73]$). The pooled empirical distributions in Fig.~\ref{fig:latency} show substantial jitter; inference-level samples characterize tails, while the interval is deliberately computed across process-level means.

Table~\ref{tab:latency} demonstrates that this result does not extrapolate to a universal multiplier. XNNPACK speedups range from 1.27$\times$ to 1.43$\times$ across thread counts, and the four-thread interval crosses unity. Batch four does not materially reduce per-image latency. Most importantly, disabling default delegates reverses the result: built-in FP32 averages 34.81 ms and built-in INT8 averages 77.42 ms, making INT8 2.22$\times$ slower. Thus, the optimized kernel path---not the file's nominal bit width---determines whether the conversion accelerates inference. This observation is consistent with benchmark literature that treats software stacks and hardware as first-class experimental variables \cite{reddi2020mlperf,reddi2020mobile,banbury2021mlperf}.

\subsection{Packaging is measurable}

The production container is 339.58 MiB uncompressed. Across five clean starts, median time from Compose invocation to the first successful health response is 1.69 s (range 1.67--2.09 s); ready-state RSS is 65.58--65.75 MiB. After warm-up, 200 sequential localhost requests have mean 49.39 ms, p50 46.34 ms, p90 62.88 ms, and p99 71.85 ms. RSS after the request run is 77.36 MiB. These figures include image upload, decoding, preprocessing, inference, and response serialization, and therefore answer a different question than native kernel timing.

\subsection{Threats to validity}

The paired accuracy inference applies to this fixed 3,925-image subset; Imagenette does not replace full ImageNet evaluation. Latency was measured on one x86-64 host, not ARM, a neural accelerator, or a battery-powered target. Interactive applications remained open and sampled pre-run CPU load varied, so process-level intervals are more credible than any single run but do not emulate an idle laboratory host. The Windows-hosted Docker measurement includes virtualization and loopback transport and should not be generalized to native Linux. Five restarts provide only four degrees of freedom, leading to visibly wide intervals. Energy, temperature, concurrent-request throughput, and multi-model generality remain unmeasured.
